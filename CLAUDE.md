# WhaleX — working notes

Rules and hard-won facts for anyone (human or agent) changing this repo.

## Versioning

Pre-1.0, both artifacts follow the same rule, each on its own number:

| Digit | When | Examples |
|---|---|---|
| **MINOR** `0.X.0` | A capability that did not exist before — something a user can point at and use. | phone pairing, 11-language UI, in-app update check |
| **PATCH** `0.x.Y` | Everything else: bug fixes, copy, layout, refactors, and repairs to a flow that was meant to work already. | a broken WebSocket handshake, mis-wrapping settings rows |

Fixing something that was supposed to work is a PATCH, not a feature.

The desktop (`apps/desktop` + all `packages/*`) and the Android app
(`apps/mobile`) ship as **separate artifacts on separate schedules**, so they
carry **separate version numbers**. Never sync them for tidiness.

Always set versions through the script — it owns every file, including
`apps/mobile/app.json`, and climbs Android's `versionCode` (Android refuses an
install that does not advance it):

```bash
pnpm bump 0.9.0                  # desktop + packages
pnpm bump 0.9.0 --mobile 0.3.0   # …and the Android app
pnpm bump --mobile 0.3.0         # the Android app alone
```

## Releasing

Work happens on `improve/roadmap`; tags are cut from that branch and `main` may
lag. The tag is what ships.

```bash
pnpm bump <ver> [--mobile <ver>]
git commit -am "build: v<ver>"
git tag v<ver>
git push origin improve/roadmap v<ver>     # the tag triggers release.yml
# CI creates the release as a DRAFT — it is invisible to the updater until:
gh release edit v<ver> --draft=false --latest
```

CI runs `pnpm install --frozen-lockfile`, so a dependency added to the lockfile
but not to its `package.json` (or vice versa) fails the build in seconds even
though the local build is fine. After any `pnpm add`, confirm both files
changed — interrupted installs on this machine have written only one.

The Android APK is not built by CI. Build it locally and attach it to the
desktop release:

```bash
cd apps/mobile/android && ./gradlew assembleRelease -g C:/gradle-home
gh release upload v<ver> apps/mobile/whalex-mobile-<mobile-ver>.apk --clobber
```

## Strings

Every user-facing string for **both** apps lives in `packages/i18n`, in all
eleven languages. **Search for an existing key before writing a new one** —
permission buttons, mode names and their hints, `transcript.interrupted`,
`code.copy` and friends are already there, and a second phrasing for the same
idea is how the two apps drift apart. `pnpm --filter @whalex/i18n test` fails on
a locale missing a key, carrying a stale one, or dropping a `{{placeholder}}`.

## Android builds on this machine

`apps/mobile/android` is generated by `expo prebuild` and gitignored. After any
prebuild, re-apply the local workarounds:

```bash
node apps/mobile/scripts/android-local-fixups.mjs
```

They exist because the Windows username is non-ASCII, which breaks AGP's prefab
step through `java.io.tmpdir`; the Gradle worker also needs the toolchain's own
JDK. Anything that must survive a prebuild (e.g. `usesCleartextTraffic`) belongs
in `app.json` under `expo-build-properties`, never hand-edited into the
manifest.

## Seeing the UI

Neither app needs a device to review:

The desktop imports `@whalex/i18n` from its **`dist/`**, not its source, so a
string you just edited will not appear until that package is rebuilt. Any
screenshot run that involves changed copy starts with both builds, in order:

```bash
pnpm --filter @whalex/i18n build && pnpm --filter @whalex/desktop build
```

```bash
node scripts/settings-shots.mjs            # desktop Settings tabs, throwaway profile
cd apps/mobile && EXPO_PUBLIC_DEMO=1 pnpm exec expo start --web --port 8090
node apps/mobile/scripts/shoot.cjs docs/shots http://localhost:8090 ko
```

The mobile preview seeds a sample session (`src/demo.ts`); query params pick the
screen (`?screen=chat&permission=1&menu=1&lang=ko`).
