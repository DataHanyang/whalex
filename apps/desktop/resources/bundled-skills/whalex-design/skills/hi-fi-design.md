# Skill: hi-fi-design

**트리거**: "디자인해줘"류의 모든 하이파이 디자인 요청 — 화면, 랜딩, 컴포넌트, 브랜드 결과물. 다른 제작 스킬(make-a-deck, make-a-prototype 등)에 들어가기 **전에** 이 프로세스를 먼저 탄다.

**목적**: 백지 출발을 막고, 맥락 수집 → 가정 표면화 → 빌드 → 검증의 프로세스로 완성도를 끌어올린다.

## 프로세스 (todo 리스트로 관리)

### 1단계 — 질문
- discovery-questions 프로토콜로 결과물 종류·충실도·옵션 수·청중을 확정한다.
- 디자인 시스템/코드베이스/스크린샷 유무를 **반드시 질문**한다. 없다고 답하면 그때 frontend-aesthetic-direction으로 룩을 함께 정한다.

### 2단계 — 맥락 수집 (가장 중요)
- 좋은 하이파이 디자인은 백지에서 나오지 않는다. **맨땅 목업은 최후의 수단**이다.
- 순서대로 시도: ① 사용자의 코드베이스/기존 화면 → ② 브랜드 사이트 CSS 실측(색·폰트) → ③ 사용자가 준 스크린샷/피그마 캡처 → ④ 그래도 없으면 사용자에게 요청.
- 관련 컴포넌트·예시는 **전부** 복사해 읽는다. 일부만 보고 흉내 내지 않는다.

### 3단계 — 가정 문서 먼저
- 파일 상단(또는 첫 화면)에 가정·수집한 맥락·디자인 추론을 짧게 쓰고, 결과물 자리는 플레이스홀더로 잡아 **일찍 보여준다**. 주니어 디자이너가 매니저에게 방향을 먼저 확인받는 방식이다.

### 4단계 — 빌드
- 매체 스킬(make-a-deck / make-a-prototype / flier / html-email …)의 절차로 실제 결과물을 만든다.
- 완성될 때까지 붙잡고 있지 말고 볼 수 있게 되는 즉시 다시 보여준다. 끝에 다음 단계 제안을 붙인다.

### 5단계 — 검증·반복
- accessibility-audit / ai-slop-check / hierarchy-rhythm-review를 돌리고 고친다.
- 아이콘·사진 등 실자산이 없으면 **어설픈 흉내보다 명시적 플레이스홀더**가 낫다 (줄무늬 박스 + 모노스페이스 설명 텍스트).

## 옵션을 보여줄 때 — 두 가지 형태 중 선택

| 상황 | 형태 |
|---|---|
| 프로토타입 성격이 강함, 옵션이 적음 | 풀사이즈 반응형 1개 + Tweaks 패널 (make-tweakable) |
| 디자인 탐색 성격, 옵션 3개 이상 | **옵션 스택** — options 스킬의 턴 스택 마크업 |

- 변형은 by-the-book에서 시작해 갈수록 창의적으로: 기존 패턴 준수형 / 색·타이포 리믹스형 / 새 레이아웃·메타포형을 섞는다.
- 목표는 "완벽한 1안"이 아니라 사용자가 **섞고 고를 수 있는 축별 변형**이다.
